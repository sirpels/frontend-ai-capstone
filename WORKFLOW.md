# FlyRank contact-form workflow learnings

The vague-contact-form branch was a basic implementation: it rendered a simple contact screen, accepted name/email/message fields, and ran generic validation. It did not handle the full set of requirements in the assignment. The branch was understandable and lightweight, but it was also noticeably weaker in correctness and edge-case handling. It did not validate phone numbers, did not enforce message length limits, and did not distinguish clearly between validation errors, submit failures, and success states.

When the prompt became specific, the implementation changed substantially. The specified-contact-form branch introduced a reusable ContactForm component, explicit validators for Full Name, Email, Phone Number, and Message, accessible label/error associations, a simulated submit sequence, and exact success/error messaging. It also preserved submitted values on validation and submission failure while clearing inputs only after a successful submission.

The biggest improvement came from explicit requirements, constraints, edge cases, and verification steps. The vague prompt left room for interpretation, which resulted in a generic form that could pass a basic test but not the assignment. The specific prompt forced the implementation to address real constraints: international names, phone formats, min/max message length, character count, accessibility, preserved values, and required success text.

Compared with the vague implementation, the specified one was better in correctness, accessibility, validation coverage, edge-case handling, UX, error/loading behavior, and maintainability. The vague version was easy to read but weak in real-world behavior; the specified version was more complex, but the complexity was purposeful and aligned with the task. Review effort was higher for the specified branch, but it was justified because the behavior had to be checked against documented requirements.

AI output still needs human verification. One concrete mistake we caught during browser testing was that after the initial success state appeared, the form fields still contained the user’s submitted values. I flagged this issue, and the AI then traced the submit flow to the root cause: the form state was not being reset after a successful submission. The fix was to clear the form values only on a successful submit while preserving them on validation failures and failed submissions. We re-ran browser verification after the fix and confirmed that successful submissions cleared the fields while failed submissions still preserved the entered values.

One limitation remains: the submission is simulated rather than connected to a real backend. That is acceptable for this assignment, but it means the app does not represent a true production submission flow. The lesson for future frontend work is that I would use AI to draft implementation quickly, but I would pair it with precise requirements and verification steps before accepting anything.
