# FlyRank contact-form workflow learnings

The vague-contact-form branch was a basic implementation: it rendered a simple contact screen, accepted name/email/message fields, and ran generic validation. It did not handle the full set of requirements in the assignment. The branch was understandable and lightweight, but it was also noticeably weaker in correctness and edge-case handling. It did not validate phone numbers, did not enforce message length limits, and did not distinguish clearly between validation errors, submit failures, and success states.

When the prompt became specific, the implementation changed substantially. The specified-contact-form branch introduced a reusable ContactForm component, explicit validators for Full Name, Email, Phone Number, and Message, accessible label/error associations, a simulated submit sequence, and exact success/error messaging. It also preserved submitted values on validation and submission failure while clearing inputs only after a successful submission. The actual Git diff between the two branches shows the specified implementation was much closer to the prompt’s requirements and much stronger in real-world behavior.

The biggest improvement came from explicit requirements, constraints, edge cases, and verification steps. The vague prompt left a lot of room for interpretation, which resulted in a generic form that could pass a basic test but not the assignment. The specific prompt forced the implementation to address real constraints: international names, phone formats, min/max message length, character count, accessibility, preserved values, and required success text. These details materially improved correctness, user experience, and maintainability. The code also became easier to review because each requirement had a direct implementation path.

Compared with the vague implementation, the specified one was better in correctness, accessibility, validation coverage, edge-case handling, UX, error/loading behavior, and maintainability. It also had a clearer review story because requirements were mapped directly to code. The vague version was easy to read but weak in real-world behavior; the specified version was more complex, but the complexity was purposeful and aligned with the task. Review effort was higher for the specified branch, but it was also more justified because the behavior had to be checked against documented requirements.

AI output still needs human verification. Even with a detailed prompt, the model can produce a plausible implementation that looks correct without fully meeting every requirement. The branch comparison showed that the “better” implementation was not just a result of more text in the prompt; it came from explicit constraints and verification against actual behavior. This taught us that AI is useful as an implementation tool, but not something to accept blindly. It should be treated as a draft that must be checked against requirements, code diff, and runtime behavior.

One limitation remains: the submission is simulated rather than connected to a real backend. That is acceptable for this assignment, but it means the app does not represent a true production submission flow. The lesson for future frontend work is that I would use AI to draft implementation quickly, but I would pair it with precise requirements, explicit verification steps, and a disciplined review against the actual diff before accepting or shipping anything.
